# Time Teller + Sound Safari acceptance protocol

This folder holds a bounded Playwright callback and Python runner for the already-leased `amari-targeted-contained` page. The callback receives that page; it must never create a browser, context, tab, profile, or session. Root runs it against the existing local preview and canonical site with the exact compiled arcade entry and source/runtime SHA for each build.

## Acceptance matrix

Run at 390×740 and 1440×844 for both `http://127.0.0.1:5180` and `https://dinospace.netlify.app`. Each game has three chapters, six normal questions per chapter, and six replay questions per chapter: 72 answered question rows per viewport/build. Time Teller replays must score lower by recording a wrong response on every mission and a visible hint on the first. Sound Safari has no star-rating field; its replay rows exercise same-question wrong-response recovery and a visible clue on each challenge, while verifying the earned badges and parent rewards remain unchanged. Enter through the normal Amari picker, learning world and game catalogue; choose chapters only through visible chapter/map controls. The main task, model controls, retry, Next, and Finish must be fully visible without scrolling before use. Secondary chapter navigation may scroll.

Derive answers from visible prompts and visible teaching models. Time Teller must check both read-clock questions and set-hand questions. Set time through the visible hand-selection/clock controls; exercise an actual drag/touch interaction on a visible clock at least once where the setting task is available, then verify the displayed time and hand angles. Wrong responses stay on the same question; a visible hint is used on the lower-rated replay. The worked explanation and packaged explanation audio remain available until the visible Next/Finish action.

Sound Safari must cover sound recognition, blending and segmentation. Use the visible sound/picture/sound-order model, including a wrong response that remains on the same challenge and a visible clue. Play the six supported packaged phoneme recordings through the UI and confirm playback advances; also exercise the authored blend/segment sequence and explanation audio. On every sound-on row, assert that the visible “Visual practice” assisted banner does not appear after target, retry/clue, or explanation clips. On the first lower-rated segmentation replay, select the correct visible phoneme sequence, temporarily mute through the visible preference control before “Check sounds”, verify the expected assisted banner and that Check sounds remains at least 44×44 and wholly in view, restore sound through the visible control, then submit. This one explicitly muted sample is the only row allowed to retain the assisted banner until Next. Reports distinguish browser playback evidence from a human judgement of pronunciation or listening quality.

Every interactive control used or audited must be at least 44×44 CSS pixels, wholly inside the viewport, pointer-enabled, and center-hit. Passive models and explanatory text must have visible, non-zero bounds. No answer, run queue, or progress state may be read from hidden component data or injected into the page.

## Save, reward and reload checks

For each game, snapshot the exact effective local progress key, all localStorage keys, sibling/protected state, sound preference, and the namespaced parent rewards record. Verify completed chapters, best stars where supported, positive receipt deltas, exact reserved parent tokens, claimed markers, parent points deltas, reload retention, ordinary return to the parent world, and no duplicate payment after an equal/lower replay. Component callbacks may pass `delta × 4` adapter units; the parent token amount and points increase must equal the receipt delta. Sound is turned on only through the visible preference control when needed and restored before comparison and during failure cleanup.

At 390×740 only, fault tests use the natural queue/completion/reward flows and exact logical localStorage key. Time Teller records selected question IDs in progress and holds the same seeded run in memory, so test its visible same-run retry, held completion local-write/readback retry, and—only when an initial saved chapter has a positive star delta—a parent-write/readback fault and same-page reload with intro receipt recovery. Restore `Storage.prototype` immediately after each controlled action and verify the same token/delta is claimed once with its local marker confirmed. Sound Safari does not persist a planned queue: chapter selection performs a strict progress/reward read and latches the run in component state, so there is no queue-write fault branch. Its already-earned badge replay can exercise local completion write/readback retry, but the retained native and canonical profiles have all three badges and no natural positive reward receipt; parent reward fault and pending-receipt reload browser branches must be marked unexercised. Eligibility is computed from the initial saved completed/best-star records only. Never clear, seed, or otherwise manufacture eligibility. If prior accepted runs have capped all chapters, record that branch as unexercised and retain earlier source-matched fault evidence rather than forcing a reward.

## Runtime, limits and evidence

The runner validates the active browser lease and retained synthetic QA profile, exact served entry path, source/runtime SHA format, bounded JavaScript response and local build identity. Provider/API requests are blocked before navigation. Reinstall the page media observer immediately after every document navigation or reload, then verify the namespaced flag and exact runtime entry. Collect runtime/console/request/asset errors, provider attempts, exact storage changes, question rows, audio advancement, touch/hand evidence and result lineage. The exact source files and driver/runner hashes are recorded in every report.

Ordinary waits and every question/model loop are bounded; the subprocess hard limit is 30 minutes. Keep one structured report per run and one viewport screenshot only on failure. The folder must remain below 8 MiB and the callback/runner/protocol source below 150 KiB combined. Never overwrite failed reports or delete unique failure evidence.

A passing report proves only the recorded journey, viewport, profile, and exact build. Browser playback events prove that packaged files started and advanced; they do not prove that phoneme pronunciation or listening comprehension is correct. The segment word is read from its visible caption/figure label, and phonemes are derived from that displayed word. Reports do not certify a physical device, other browser engines, or an unrecorded deployment. Production, native, and any unexercised fault branches remain distinct in the final summary.

The intentional mute sample also removes and re-adds the last sound through the visible tile while muted. This is actual visual practice, so its assisted marker should remain after sound returns; merely toggling preference after already hearing every input does not create that persistent marker.
