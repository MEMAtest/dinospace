# Subtraction Station + Number Line Jump acceptance protocol

This folder contains a bounded visible-control Playwright callback and a runner for the existing leased `amari-targeted-contained` page. The callback receives that already-owned page and does not create a browser, context, tab, profile, or session. The runner verifies the active lease, retained synthetic profile path, live document and exact compiled arcade entry before dispatch.

## Acceptance matrix

Root runs the full driver at 390×740 and 1440×844 against both `http://127.0.0.1:5180` and `https://dinospace.netlify.app`, supplying the exact entry and 40-character source/runtime SHA for each build. Each journey enters through the regular Amari picker, Maths Missions world and game catalogue. It completes all three chapters for both games, with six normal questions and six deliberately lower-rated replay questions per chapter (72 question rows per run). Start/Continue/replay/map controls must follow the visible progress state; the primary journey never depends on hidden run queues, seeded answers, DOM test attributes that reveal an answer, or storage mutation.

Answers are derived only from the visible prompt and rendered teaching model. Subtraction uses the countable take-away scene, aligned compare-pair diagram, or story amounts. Number Line Jump uses the visible starting/landing numbers, number-line labels and rendered route; hop chapters advance with the visible forward/back controls. Wrong responses keep the current model/question, visible hints and authored model interactions are exercised, and the worked explanation stays until the visible Next or Finish control is activated. Packaged “Hear question/mission” and explanation audio are played through the visible buttons. Fault retries and primary controls must be at least 44×44 CSS pixels, fully inside the viewport, center-hit and pointer-enabled before each click. Secondary chapter/card navigation may scroll; primary questions, model controls, retries, Next and Finish may not.

The normal result aims for the natural three-star threshold, preserving a positive delta for any eligible saved chapter. The lower replay deliberately records wrong attempts and then selects the visible correct response (or uses visible one-step hops in the hop chapter), yielding a lower current rating. The saved best and parent totals must not regress or be paid twice. Every parent return is checked through the visible parent route.

## Storage, rewards and reload

The target local keys are `amari_subtraction_progress_v1` and `amari_numberline_progress_v1`. The runner snapshots all localStorage before/after each game and permits only the target key, the shared Amari rewards record and the documented common gameplay/sound keys. Askia, sibling games, other child state, IndexedDB and unrelated protected keys remain unchanged. The original sound preference is read from the visible toggle, enabled only when needed for packaged playback, restored before final snapshots, and restored again during failure cleanup.

Receipt IDs, positive star deltas, claim markers and reserved tokens (`dino:subtraction:<receiptId>` and `dino:numberline:<receiptId>`) are reconciled against the actual parent record. Components pass `delta * 4` callback units to the shared adapter; the parent claim and points delta equal the receipt star delta. The local claimed marker must follow a persisted parent claim. Lower replay checks each chapter's best stars and parent reward record are byte-identical across the replay. Final same-page reload checks the complete localStorage inventory byte-for-byte.

At 390×740 only, the driver injects a write fault on each game's natural start queue and, for the first naturally material chapter, local completion write/readback plus parent reward write/readback faults. A second naturally material chapter receives a parent-write fault followed by same-page reload and automatic intro receipt drain. Eligibility comes only from the pre-run saved completion/best-star snapshot; a completed legacy chapter with no known rating is not treated as material. If all chapters are capped or another material chapter is unavailable, that branch is explicitly marked unexercised rather than manufactured. Each fault wrapper targets only its exact logical key and restores `Storage.prototype` immediately after the controlled click. Reports retain the question row, receipt and intermediate parent evidence.

## Runtime, bounds and evidence

The runner verifies the exact served `/assets/arcade-*.js` and records the source/runtime SHA, response hash, source hashes, lease owner, viewport, rows, storage/reward evidence, provider attempts and runtime errors. Provider routes are blocked before navigation. Guards are installed before navigation and media observation is reinstalled after every full document navigation or reload. Ordinary UI waits and per-question count loops are bounded; the entire runner has a 30-minute hard timeout. Failed runs retain structured JSON and one viewport screenshot; successful runs do not retain screenshots. The evidence folder is capped at 8 MiB and refuses report overwrites.

A passing report proves only the recorded browser journey, viewport, profile, and build. It does not certify a physical device, listening comprehension, all browser engines, or unrecorded canonical/native routes. Keep failed reports as failed and state unexercised branches explicitly.
