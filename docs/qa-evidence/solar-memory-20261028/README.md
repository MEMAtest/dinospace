## Source findings and decisions

### Solar System

The current component already has a strong interactive Three.js orrery, responsive nine-world planet strip, fact cards, compare copy, challenge per destination, quiz option shuffling, and a durable fact/challenge passport. `PLANETS` includes Pluto and explicitly calls it a dwarf planet. Keep this work and the existing 3D/model/art pipeline; do not replace it with static cards.

The journey is currently browse-first: any destination, fact cards, optional details, then an optional one-question challenge. There is no stable authored mission/run contract or clear discovery-to-compare-to-challenge route. Quiz option seed is generated at component mount rather than an explicit mission start and saved mission identity. More materially, `storePassport` updates in-memory state and returns false on storage failure, while fact and challenge handlers still proceed as if saved; it has no retry transaction. Badge/quiz reward effects must follow a successful first durable write, and replays must not farm them. The component currently lacks `onPhaseChange` and narration-cancel wiring, uses live `useGameDifficulty` with one mount-level random seed, and `seededPlanetOptions` duplicates and de-duplicates options rather than performing a direct deterministic shuffle. Bind mission difficulty, destination and choices at the ordinary mission start so feedback/replay cannot silently change a question. Current sound path can request generated speech for text without proving a matching packaged recording. For this release, rely only on exact existing, source-bound offline recordings; otherwise show readable instructions/facts and omit audio action. Do not add provider/device speech fallback or request more clips.

**Pair 4 scope:** retain free exploration, but add a clear optional `Discover → Compare → Challenge` mission for each of the eight planets plus Pluto. Make planet/dwarf-planet classification explicit in Pluto's strip/fact cues; use the existing fact/compare/challenge content and 3D assets. Seed a stable mission and answer-option ordering when a mission starts; prevent question/answer identity from changing during feedback. Save completion before showing a collected badge/reward, surface write failure with a Retry action, make unlock/reward idempotent, and keep the passport/read-only badge view durable across reload and child boundary. All nine destinations remain directly accessible; the mission may resume/replay without weakening existing progress. Keep currently working rotate/tilt/zoom/overview and scroll/touch behavior.

### Memory Match

The existing ten Amari boards use pair counts `4, 8, 10, 12, 13, 14, 15, 16, 17, 18`, illustrated card assets, seeded layouts per run, mismatch locking, wrong-pair guidance, held completion fact, prior best-move/sticker passport, reload resume and a read-only shelf. Preserve this progression and current card/art layouts. Askia/little mode is outside the Amari pair contract and must remain intact.

The current coach has only a few repeated messages, mostly keyed to board index or an efficient result captured once at visit start. It does not teach a changing scan/group/recall strategy as density rises, nor reliably reflect a prior completed run after the same component has mounted. `finishLevel` currently presents completion before storage returns. `completeMemoryBoard` withholds stars on write exception, but returns an in-memory passport containing the unsaved sticker; completion advances and the screen has no targeted sticker-save Retry. `completeMemoryProgress` can similarly report resume failure while separately attempting level save. Verify the effective stored state before calling a badge or chapter saved, and do not make unsaved completion appear on the read-only shelf. Keep retries on the same completed board, preserving move count and result.

**Pair 4 scope:** preserve all ten boards and counts, deterministic normal progression, fresh replay layouts and pair integrity. Provide a short age-appropriate scan/group/recall tip that evolves across the 4→8→10→12→13+ density steps; teach the next technique only when board load changes. Use saved prior-run outcome for later visits/replays, not transient current-run results, so coaching is stable during a run. Keep mismatch delay/cancellation, focus, keyboard/touch and completion fact. Make final board sticker/progress writes failure-aware, with an accessible Retry that reattempts the same result; award progress/rewards exactly once after successful persistence, and keep failed writes off the earned shelf. Resume after reload at the existing unlock and preserve best moves/stars. Exact parent return is Thinking & Play.
