## What the source already does

This section records the pre-implementation baseline only; the implementation addendum below supersedes the baseline gaps where it documents a fix.

### Rocket Builder

- Five levels contain two or three builds apiece. Missing parts become a shuffled tray; levels progress from nose/fins to full builds, introduce five colours, and end with the full colourful rocket. Successful placement starts a spoken 3–2–1–Blast Off animation.
- Before this pair, each part used a broad rectangular tolerance and children could drag or tap parts on the canvas. The implementation replaces that broad test with narrow authored snap zones plus small authored-center pointer windows for the full body and composite fins. Named keyboard targets validate the selected part's target identity; the transparent gap between the two fins does not make the two fin-side keyboard targets interchangeable.
- `ROCKET_PARTS` and the component fallback provide authored SVG rocket/ghost geometry. The game did not have the five `rocket-{nose,body,window,fins,flame}` raster part files named by `docs/image-brief.md`; those component pieces used the simpler SVG drawing. The standalone `fuel-rocket.webp` is a polished red rocket used by Fuel Up, while Rocket Builder's start/payoff also rendered the composed SVG pieces rather than that standalone raster.
- The board is `role="presentation"`; selecting a piece is keyboard-capable through `DragItem`, but there is no keyboard-focusable placement target. A wrong part only shakes, plays a cue and updates the shared mistake count; it does not provide a held, readable placement explanation. The wrong-reset timeout is not cleaned up with the round timers.

### Fuel Up

- Five levels grow the target pools from 1–3 through 5–10. Askia has 3/4/5/5/5 rounds; Amari enters at the existing level-3 floor. Levels 1–2 auto-launch at the exact target. Later levels allow larger tanks and require a Launch button.
- Number and dot cues show the target; the tank is a progress bar; children can tap a can or drag it onto the rocket. At later levels, launching with the wrong count shakes and empties the tank after 700 ms. That removes the child's visible count rather than explaining how to adjust it. Current can buttons all expose the same accessible name `Fuel can`.
- Level 5 has six possible targets but only five rounds per play. Current seeding is stable within a mounted play but picks a random order by mount/play id, so one target is omitted each play without an explicit rotation guarantee.
- Wrong-reset and exact-launch `setTimeout`s are not cancelled on round unmount.

### Shared small-child shell, storage and narration

Both games run through `LittleGameShell` for Askia and Amari. The shell provides the start/finish pages, level dots, star/reward animation, and parent navigation. Its level dots are informational, not level selectors. It auto-advances rounds after a fixed delay, and awards the game result/rewards even when `recordLittleResult()` cannot write. The shared little-progress reader turns blocked or malformed storage into an empty object; the default getter can throw while reading `window.localStorage`. Broad changes would affect six other little games, so Pair 5 uses an opt-in pair-only saved-completion contract and a bounded regression on the opt-in shell path. It must not claim acceptance for games outside Pair 5.

The existing authored narration inventory has 86 unique little-game strings. All 86 resolve through `getOfflineVoiceClip` and have local packaged files, including the current Rocket Builder and Fuel Up lines. No new voice work is required. The current components pass strings directly to `speak`; pair-owned speech must explicitly check the exact packaged clip and use `premium:false`, with visible text instructions retained when a clip is absent. No device/provider fallback or paid generation is permitted.

## Artwork decision

Fuel Up's `fuel-rocket.webp`, `fuel-can.webp`, and `bg-fuelup.webp` are present and visually strong; retain them. Rocket Builder's own baseline start/payoff and assembly all used the SVG part drawing; it did not render the standalone Fuel Up rocket. This is a concrete visual mismatch with the polished existing Fuel Up rocket. Retain the SVG fallback and current geometry. The planned improvement is one coherent, transparent, colour-neutral set of five part illustrations aligned to `ROCKET_PARTS` viewBox boxes, with tintable nose/fins and an empty, high-contrast body window so the assembled whole matches the existing full rocket. Keep all generated/edited imagery within the existing asset budget and verify both the assembled result and each part at 390px/1440px. Root owns any image-generation work and provenance review; no large download or full-asset copy is needed. The five lazy public WebP sprites and their source hashes/prompts now exist in `docs/qa-evidence/rocket-fuel-20261028/art-provenance.json` (83,542 runtime bytes); they improve Rocket Builder's start, tray/assembly, and payoff while preserving the SVG fallback.
